### 研究问题

1. **风险来源**：生成代码自身的漏洞、恶意训练投毒、检索上下文污染、不存在的依赖包和长期记忆偏好分别如何影响软件供应链？

### [01] Security Weaknesses of Copilot-Generated Code in GitHub Projects: An Empirical Study


原始笔记：[core/paper_01.md](core/paper_01.md)。

paper_id: doi:10.1145/3716848。作者：Yujia Fu, Peng Liang, Amjed Tahir, Zengyang Li, Mojtaba Shahin, Jiaxin Yu, Jinfu Chen；ACM TOSEM，2025。正式书目沿用已核清单；全文依据[arXiv:2310.02059v4](https://arxiv.org/abs/2310.02059)，本地34页作者稿首页DOI仍是占位符，不能把稿内卷期占位符写作正式卷期。2026-11-17完成方法、结果与局限定向全文核验，未复现实验。

#### 全文证据

- p12表2：733份代码文件/片段，Python419，JavaScript314；其中Copilot672、CodeWhisperer38、Codeium23。故733和整体弱点率不能称为纯Copilot样本统计。
- p14–18 §3.3、§4.1：CodeQL加语言专用工具（Python用Bandit，JS用ESLint），报警并集后人工检查代码与AI归属。Code标签数据需确认弱点位于带AI注释的生成片段内；人工筛选避免把邻近的人类代码误算。
- p19表4：Python124/419有弱点，JS76/314；合计200/733（27.3%）；弱点实例628。论文Python印29.5%，124/419实际29.59%，应优先保留计数。实例数与有弱点文件数分母不同。
- p24表7：295个待修CWE问题，/fix后238，基础提示后201，增强提示后132；修复率分别19.3%、31.8%、55.5%。这是报警/问题消失的修复评价，不是全部代码55.5%安全，也未证明功能保持。
- p25图17：增强提示对CWE-78是0/15，对CWE-94是6/42，对CWE-330是54/55；总体修复率掩盖明显类别差异。

#### 局限与比较提示

作者p29–30：关键词检索和人工归属有选择偏差；工具覆盖有限；仅Python和JS；样本偏向公开且自报AI使用的项目。独立判断：开发者事后修改、工具版本与模型变化影响外推；人工过滤报警并不测出未报警样本的漏报率。不能据此证明AI比人类更不安全，没有同任务因果对照。

### [02] Rethinking the Evaluation of Secure Code Generation


原始笔记：[core/rethinking.md](core/rethinking.md)。

- paper_id: doi:10.1145/3744916.3773217；预印本 arXiv:2503.15554v2。
- 作者：Shih-Chieh Dai, Jun Xu, Guanhong Tao。正式出处：2026 IEEE/ACM 48th International Conference on Software Engineering (ICSE ’26)，336–348（13页）。
- 来源：[正式会议页面](https://conf.researchr.org/details/icse-2026/icse-2026-research-track/175/Rethinking-the-Evaluation-of-Secure-Code-Generation)；[作者正式PDF](https://tao.aisec.world/assets/pdf/ICSE26.pdf)；[可下载预印本v2](https://arxiv.org/pdf/2503.15554v2)；[工件](https://github.com/Utah-SaLT-Lab/RethinkSecCodeEval)。
- 核验日期：2026-11-17；完成方法、结果、局限的全文阅读及关键表格复算。未运行模型实验。以下页码均为PDF顺序页码；正式作者PDF与arXiv v2均为13页，关键表格一致。全文文本保存 sources/rethinking_arxiv.txt。

#### 研究对象与流程（论文证据）

- 关注函数级生成技术，不是直接评价当前商业Copilot产品。比较 SVEN、SafeCoder（训练）、CodeGuard+（解码与提示约束）、PromSec（扫描器反馈迭代提示）。见p3–4、表1。
- 同一段生成代码同时接受单元测试与漏洞扫描，避免分别在两个基准测“功能”和“安全”后拼接结论。扫描器为CodeQL、Bearer、Bandit；Qwen2.5-72B和Llama3.3-70B另用于检测器质量诊断。见p4–6。
- BigCodeBench：1,140项Python任务，平均5.6个单元测试；SecCodePLT+：1,201项Python任务，平均7.5个测试。SecCodePLT+通过Qwen2.5-Coder-32B产生输入、执行参考程序产生期望输出构造。见p4表2及§3.2。
- 开源生成模型：CodeLlama-7B、Qwen2.5-Coder-7B、DeepSeek-Coder-V2-Lite、Mistral-7B、StarCoder-1B；商业模型GPT-3.5-Turbo、GPT-4o仅试PromSec。StarCoder不试PromSec。CodeGuard+部分模型缩进先自动修正；其安全提示约束还利用基础模型输出的CWE检测标签，比较条件存在优势。见p5、p8。

#### 指标与分母

- Secure@1：按指定扫描器无报警的生成样本占比，不能解释为经证明无漏洞。
- Secure-Pass@1：无任一扫描器报警且所有功能测试通过的样本比例。
- SAFE@k = (1/k) Σ_i secure_i × (exp(case_pass_i)−1)/(e−1)。case_pass是该样本通过测试的比例；secure为三扫描器都不报警的二值判断。SAFE允许功能部分正确，不等于严格功能正确率，且仍依赖测试覆盖及安全判定器。公式见p4式(1)，聚合规则p8。
- 最终联合评价没有使用LLM检测器，因为人工检查显示大量误报；不能描述成“五检测器多数投票”。见p8。

##### 复算与论文内部不一致（研究者核查，非作者结论）

1. 表3人工样本中真实有漏洞21例、无漏洞21例，合计42？注意表3各行合计42（2+21+0+19=42），而正文称抽取44例。这是另一处需核对工件的样本数不一致，不应强行补出2例。
2. 按表3标准定义 FPR=FP/(FP+TN)：Qwen=18/21=85.71%，Llama=21/21=100%；CodeQL FNR=19/21=90.48%。作者p6的“nearly 50% false positive rate”可能更接近FP/正文44的比例，但未核实其实际分母，不应直接当标准FPR引用。所有数值仅适用于该小样本，不能外推全基准。
3. p8正文称GPT-3.5的SAFE由0.4445降至0.381下降28%；按表5原值复算相对降幅为14.29%，绝对降幅0.0635。Secure-Pass由0.3219降至0.2447的相对降幅为23.98%。报告优先使用原值，并说明文字百分比不一致。

#### 局限：作者承认与独立判断

作者在p10–11 §5承认：静态分析器仍会漏报；任务主要是Python；SecCodePLT+测试由LLM生成且未人工全面验证边界覆盖；数据污染不能排除；并未重复所有实验。一次完整运行约430 A100 GPU小时，Qwen重复三次共约1,290小时（p11）。人工安全检查至少两作者审阅，分歧由第三作者解决（p10）。

独立判断：多工具并集减少部分漏报，但可能累计误报；“零报警”的secure_i仍只是操作定义。SAFE的指数映射是设计选择，不能自动表明部分通过的代码具有部署价值。小样本混淆矩阵和全样本扫描分数应分开呈现。没有动态利用验证就不能称每个报警都已证实可利用。

#### 与课程研究问题的连接（分析提示，需作者自行形成论证）

- 比较表应同时放功能测试、扫描器规则覆盖、人工核验、联合指标、成本，不能只按安全分数排序。
- FPM方向：分别问误报过滤提升precision多少、漏报是否增加；至少保留TP/FP/TN/FN原始计数和适用范围。
- RAG方向：检索到安全知识后，还须核验版本、代码语境和可执行证据；该论文没有直接证明RAG或FPM一定有效。

### [03] Can You Really Trust Code Copilot? Evaluating Large Language Models from a Code Security Perspective


原始笔记：[core/copilot.md](core/copilot.md)。

- paper_id: doi:10.18653/v1/2025.acl-long.849
- 日期：2026-11-17。证据等级：已阅读全文主要章节、实验表1–7及附录A、D–G；未运行作者代码、未独立复现；不是作者自写综述正文。
- 正式题名：Can You Really Trust Code Copilot? Evaluating Large Language Models from a Code Security Perspective。ACL网页题名单数Copilot，PDF首页题名Copilots，引用按ACL元数据。
- 作者：Yutao Mou, Xiao Deng, Yuxiao Luo, Shikun Zhang, Wei Ye。
- ACL 2025 Long Papers, pp.17349–17369。DOI: 10.18653/v1/2025.acl-long.849。
- [正式记录](https://aclanthology.org/2025.acl-long.849/)；[全文](https://aclanthology.org/2025.acl-long.849.pdf)；[作者代码](https://github.com/MurrayTom/CoV-Eval)。本地sources/copilot.pdf和copilot.txt。
- 以下定位采用印刷页码；PDF页码=印刷页码−17348。

#### 问题与方法（结构笔记）

- 对象：通用/代码LLM的代码补全、漏洞修复、漏洞二分类检测、CWE多分类四项任务，不是专门对商业GitHub Copilot产品的受控实验。
- CoV-Eval：GitHub-CWE为种子，54场景（C 25、Python 29），18类CWE；现成Codex生成有效程序1084个，其中477个有漏洞。出处§3.1，p.17351。
- Vul-Evol：GPT-4o通过增加约束、替换需求、增加推理步骤、提高复杂度需求扩增270场景。人工过滤已经包含安全检查的上下文；因此是经过漏洞诱导筛选的任务，不能直接解释为自然开发分布漏洞率。出处§3.3，p.17352；附录D，pp.17363–17364。
- VC-Judge：Llama3-8B-Instruct微调。把已知场景CWE和描述放进判定式提示，让模型判断特定漏洞；与无先验的开放世界漏洞发现任务有区别。出处§4，pp.17352–17353。
- 训练来源：CoV-Eval生成代码216条、CoV-Eval检测集531条、BigVul4486条；经判定/分类/修复任务模板构成14952训练样本。出处表9，p.17364。复现前应进一步审计同源场景训练/测试去重，不能仅据同源判定存在泄漏。
- 设置：20模型=4闭源+11开源通用+5开源代码；开源temperature=0.6，top_p=0.9；每项一次推理。微调学习率5e−6、3 epochs、8×A800 80GB。出处§5.1–5.2，pp.17353–17354。

| 层级 | 可以确认什么 | 不能确认什么 | 需要保存的证据 |
|---|---|---|---|
| 静态报警 | 规则匹配或可疑数据流 | 实际可利用性、全部漏洞均被覆盖 | 工具版本、规则集、路径和源码位置 |
| 多工具一致 | 多个检测器给出一致判断 | 独立性与无共同盲点 | 每工具原始输出和分歧集合 |
| LLM审查 | 模型给出问题类别与解释 | 解释忠实、漏洞确实存在 | 模型版本、提示、输入范围、引用片段 |
| RAG证据 | 找到可能相关的安全知识 | 该知识适配当前版本或可达路径 | 文档版本、来源、代码映射、反例 |
| 人工复核 | 在既定规范下经审查确认 | 审查者必然正确或覆盖所有负例 | 双人标注、一致性、裁决日志 |
| 测试/利用证据 | 在所给输入与环境中复现问题 | 所有输入及所有部署环境的安全性 | 最小测试、依赖锁定、环境与日志 |
| 修复后复测 | 已覆盖场景的漏洞与回归结果 | 绝无新漏洞或未覆盖分支 | 原始与修复代码、同一测试集结果 |

以上分层是本项目组织资料的建议，不是任一论文提出的统一标准；各层可以组合，不能机械视为严格强弱全序。

### 3. 指标登记规范

- 以“漏洞存在”为正类时：Precision=TP/(TP+FP)，Recall=TP/(TP+FN)，FPR=FP/(FP+TN)，FNR=FN/(FN+TP)。分母为0时记未定义，不填0。
- FP/N是总体误报占比，不是通常定义的FPR；1−Precision是报警中的误报占比，也不是FPR。
- F为功能测试通过，S为选定安全检查通过。联合通过率=数量(F且S)/总生成数；条件安全通过率=数量(F且S)/数量(F)。两者须同时登记分母。
- S只代表所用检查的通过结果。不可将“联合通过率”改称已经证明安全且正确的真实概率。
- 丢弃、拒答、语法错误、构建失败须单列。否则过滤所有代码也可能得到表面很高的安全分。
- 百分点变化=b−a；相对改善=(b−a)/a。风险下降通常写(a−b)/a。由表格重算的结果标“本项目复算”，不要归给论文。
- 按语言、CWE、任务与模型分组，保留样本量与不确定性。宏平均与微平均不得混用。

### 4. FPM与RAG可以形成的研究问题（尚未验证）

#### 问题一：减少误报是否增加了漏报？

- 比较：原始扫描→LLM过滤→RAG过滤；所有路线使用相同的代码与原始报警。
- 对照：被保留、被抑制报警都抽样人工复核；另抽未报警代码检查漏检，防止只标注正例。
- 结果：每千行人工审查成本、Precision、Recall、FPR/FNR、被错误抑制的真实漏洞数量。
- 作者任务：阐明何种证据足以抑制报警，哪些情形必须转人工；不能把模型置信度当事实。

#### 问题二：安全知识检索的适用性如何验证？

- 因素：API版本正确/过期、代码路径可达/不可达、可信/被投毒知识、是否存在相互冲突文档。
- 对照：无检索、普通检索、加入来源与版本约束、加入可达性证据。
- 结果：证据引用正确率、最终漏洞判定、错误抑制、延迟；评论相似度仅作辅助。
- 作者任务：解释与SecureReviewer、SecCoder、CodeGuarder、IoTRAGuarder的差别，不提前声称创新。

#### 问题三：防护能否在保持功能时跨威胁泛化？

- 场景：自然漏洞、恶意训练投毒、上下文污染、包幻觉和不安全记忆分别报告。
- 对照：同一代码同时做功能测试和安全核验；跨CWE、跨项目或时间划分，避免训练测试重叠。
- 结果：联合通过率、保留率、漏洞召回、任务完成率与总成本；不要把跨论文ASR拼成榜单。
- 作者任务：挑选可实施的一条路线，列出反例、失败条件与最小验证方案。



### 最小验证方案：FPM与RAG的可核查比较

本节是本项目建议，未实施实验，不是已有论文的结果或已成立的创新点。

1. 固定一批任务、每次生成代码、功能测试和依赖环境，保存生成失败与拒答，建立代码样本到检测结果的稳定对应。
2. 对同一批原始报警比较三组：原始扫描、LLM过滤、带来源与版本约束的RAG过滤。固定基础模型和输入范围，记录提示与检索内容。
3. 复核保留与抑制的报警，并另行抽查原始未报警代码。若采用分层抽样，保存各层总体数与抽样概率，估计总体指标时按设计加权，不能把抽样后的类别分布当总体。
4. 在复核范围内保存TP、FP、TN、FN与分母，报告错误抑制的真实漏洞、功能测试、保留率、人工成本和推理成本。样本不足或分母为零时明确标注，避免填入虚假的精确值。
5. 增加过期文档、错误API版本、路径不可达和互相冲突证据作为对照。检验错误来自检索、适用性判断还是最后的漏洞裁决。
6. 可证伪条件：如果减少报警的收益伴随不可接受的真实漏洞丢失，或者RAG在匹配版本与上下文后仍不优于同成本基线，就应收缩或否定对应假设。可接受损失阈值由作者结合任务说明，不由现有笔记虚设。
